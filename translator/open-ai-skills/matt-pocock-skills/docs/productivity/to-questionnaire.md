## 功能说明

`to-questionnaire` 把你自己定不了的决策变成一份**问卷**——一个 Markdown 文档,交给那个握有你缺失信息的人,让他们异步填写,或者你们俩开会时一起过一遍。

它盘问的是**发送**,从不盘问主题。在这里问主题毫无意义:不知道主题正是你要写信给别人的原因。所以它只问你总能回答的两件事——这东西发给谁、你希望从他们那里拿回什么——并把文档里每个问题都对准两者之间的**差距**。

## 何时使用

你通过输入 `/to-questionnaire` 来调用它——[Agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不会自己主动使用。

当一个决策被卡在另一个人脑子里的知识上时用它:客户、领域专家、掌握业务规则的高管、你不坐在一起的团队同事。用哪个技能取决于答案到底在哪:

| 答案在…… | 该用哪个 |
| --- | --- |
| 你自己的脑子里,还没磨利 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的脑子里 | `to-questionnaire` |
| 谁脑子里都还没有——这个问题需要有个东西来触发反应 | [prototype](https://aihero.dev/skills-prototype) |

常见场景是一场[问询](https://www.aihero.dev/ai-coding-dictionary/grilling)会话卡住了:浮出来的某些东西不是你能回答的。在同一对话里运行 `/to-questionnaire`,把这些问题的答案先取下来,再把答案带回来继续。

## 发送,而不是主题

面试只有两轮问答,然后结束。

- **发给谁?** 他们的角色、专长、与你关系。这定下语气,以及文档要承载多少背景——外部客户需要铺垫,队友不需要。
- **你想拿回什么?** 你独自解决不了的具体决策或事实。这成为成品文档的验收清单:你点名的每一项都有一个问题对准它。

之后全是起草。文件落在当前目录的 `to-questionnaire-<slug>.md`。没有配置,没有工作区,没有什么要设置的。

## 文档

它以**发现问卷**为框架——你缺背景,收件人握着它——这个框架决定了它的形态:

- 一行目的说明点出压在其上的决策,外加一小节背景,给一个从未进过你脑子的人看。
- 问题按**最重要在前**排序,归入主题标题之下,因为异步意味着你可能只有一次机会。
- 每个问题只讲一个点,绝不复合,下面留一个回答位,只在可能被误读的地方加一行*为什么这很重要*。
- 明确允许回答「我不知道」——被标记的不确定有用;一个读起来像事实的自信猜测没有。
- 结尾兜底:我们没问但你该告诉我们的,有什么吗?

有两样它刻意不是的东西。它不是**分支式**的——问题是一个扁平的分组列表,不是一棵答了 A 就跳过 D 节的树。它也不是**多人收件**——一次运行产出一份文档,给一个人。

## 常见问题

**它会读我的问询会话,从里面抽取问题吗?**
不是作为独立一步。技能没有摄入阶段:它问发送,然后起草。在问询会话之后能起作用,是因为你在**同一个对话**里运行它,所以[会话](https://www.aihero.dev/ai-coding-dictionary/session)已经在[上下文](https://www.aihero.dev/ai-coding-dictionary/context)里,起草可以取材于它。在新会话里启动,它对问询一无所知——答「你想拿回什么?」时,主题就得你自己重新补上。

**缺失的答案不全在一个人手里。它能按收件人拆分吗?**
不能。第一步问的是*那个*收件人,单数,整份文档的语气和背景都冲着他。如果三个人各握着答案的三分之一,就按人跑三次。在单份文档里按学科或角色路由问题,是有人提过的请求;不是发布的行为。

**问题之间相互依赖吗——会根据前面的答案跳过小节吗?**
不会。依赖式问题设计被探索过,没有发布。输出是一份静态文档:主题分组、最重要在前、所有问题都在。反对它的理由也是公允的——让[模型](https://www.aihero.dev/ai-coding-dictionary/model)在真实答案之前规划两个三个以上的问题,它规划得很差,而分支式文档得在每一个答案之前把所有问题都规划好。

**如果收件人也不知道呢?**
文档让他们直说。「我不知道」和部分答案是被明确要求的,被标记的不确定比猜测值钱,因为含糊的答案和自信的错误答案,一旦回到你的上下文里,看起来一模一样。

**它会把它发到什么地方吗——Slack、issue 追踪器、邮件?**
不会。它在当前目录写一个 Markdown 文件,告诉你路径。投递是你的事:粘贴进[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)、丢进 Slack 线程、作为邮件附件,或者投到共享屏幕上当场过一遍。这四种方式都有人手工接过。

**这不就是批处理模式的 `/grill-me` 吗?**
不是,这个区别值得守住。`grill-me` 已经按**轮**提问了——一次问整个前沿,再根据你的回答重算——所以「把所有问题一次给我」的需求在那里已经满足了。`to-questionnaire` 在另一个轴上:区别不在于问题怎么送达,而在于答案在谁的脑子里。自己更快地把答案答出来是 `grill-me`;把答案从别人那里弄出来是这个。

**我就不能直接让 Agent 做这个,不用技能吗?**
可以,而且它出现之前就有很多人这么做——`OPEN_QUESTIONS.md` 文件、发给客户的电子表格、每个未答问题一张「需要更多信息」工单。技能给你买来两件事:面试从不会漂到主题上,文档以非技术收件人真能填写的形态出来。如果你已有能用的内部格式,诚实的答案是你不需要这个。

## 效果如何判断

- 它问收件人、问你想拿回什么,然后就不再问了。问到主题本身,是技能脱轨了。
- 你点名的每项「我想拿回的东西」都能追溯到文件里的一个问题。
- 问题读起来对准的是*收件人*知道的东西,而不是你自己的开放问题逐字抄下来。
- 你可以把文件交给一个没参与对话的人,他们知道为什么收到它、什么时候该回复。
- 拿回的答案是新一轮问询的可用输入,而不是一组新问题。

## 在系统中的位置

`to-questionnaire` 是一个随时可用的独立工具。它坐在你自己知识的边界上,在那里,下一步是另一个人,而不是另一个技能——最常见于流程中途,规划卡在某个不该由你决定的东西上。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me),两者的分野在答案住在哪里:问询挖你自己,问卷挖别人。拿回来的是原材料——喂进另一轮问询,或者如果工作要走向构建,喂给 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。不确定哪个技能适合当下时,[ask-matt](https://aihero.dev/skills-ask-matt) 会为你导航。
