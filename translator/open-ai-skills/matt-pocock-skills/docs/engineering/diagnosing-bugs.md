## 功能说明

`diagnosing-bugs` 对疑难 bug 或性能回归执行六阶段诊断：构建复现、精简复现、排列假说、插桩、带着回归测试修复、清理。

在存在**紧密**反馈循环之前，它不允许 Agent 形成任何理论——一条具名的命令，已经实际运行过一次，在*这个* bug 上变红、修复后变绿。拿到 bug 报告的编码 Agent 的默认行为是读代码、猜答案；本 skill 挡住这条路。如果没有一条能变红的命令，就没有第二阶段。这道唯一的闸门正是 skill 存在的意义。它之后的一切——二分查找、假说测试、插桩——一旦信号存在就都是机械操作。

## 何时使用

输入 `/diagnosing-bugs`，或在任务合适时 Agent 会自动调用它——它是模型调用的，会在 "diagnose"、"debug this" 出现时，或当有人报告有东西坏了、抛异常、失败或变慢时触发。

在棘手的问题上使用它：一眼看不出原因的 bug、间歇性偶发故障、在两个已知良好状态之间悄悄出现的回归。它刻意很重，对于那些想一条消息就得到答案的问题，它是错误工具。

| 你的情况 | 去哪里 |
| --- | --- |
| 一个你能用症状描述的具体缺陷 | 本 skill |
| 一个变慢的端点或一个有已知前后对照的时序回归 | 本 skill——它有性能分支（先测基线，再二分） |
| "这个代码库的瓶颈在哪里？"——没有具体症状 | 不是本 skill。它诊断一个已知的故障，它不做普查 |
| 一份来自他人的原始 bug 报告，尚未确认或成文 | 先走 [triage](https://aihero.dev/skills-triage) |
| 一次性代码，用来回答设计问题而非追查缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 先测后写地构建一个计划中的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 没有好接缝可以锁死这个 bug | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)——本 skill 自己会向它交接 |

## 紧密循环就是 skill

第一阶段投入了不成比例的努力，因为它是唯一困难的阶段。skill 给出了构建循环的方法阶梯，大致按偏好顺序：

1. 在能触达 bug 的接缝处写一个失败的测试。
2. 针对运行中的开发服务器写一个 curl 或 HTTP 脚本。
3. 用固定输入调用 CLI，与已知良好的快照做 diff。
4. 一个无头浏览器脚本，对 DOM、console 或 network 做断言。
5. 重放捕获——保存的请求、载荷或事件日志，隔离地跑过代码路径。
6. 一次性辅助工具：系统的一个最小子集、一次函数调用。
7. 属性测试或模糊测试循环，用于"输出偶尔是错的"。
8. 一个可以交给 `git bisect run` 的二分工具。
9. 差分循环——同一输入，旧版对新版。
10. 一个 [人在回路中](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) 的 bash 脚本，最后手段。skill 为此附带 `scripts/hitl-loop.template.sh`：Agent 运行脚本，你在终端里跟着提示走，你的回答以可解析的输出返回。

*一个*循环不是目标。**紧密**才是：快（秒级）、确定（每次运行同一结论）、尖锐（断言你确切的症状，而非"没崩"）、可无人值守地由 Agent 运行。一个 30 秒且偶发失败的循环比没有好不了多少。对于一个只是偶尔出现的 bug，目标不是干净的复现，而是**更高的复现率**——循环触发、并行化、加压、注入 sleep，直到偶发率足够高、可以对着调试。

当它确实建不出循环时，指示它停下并明说，列出尝试过的东西，然后向你请求 [环境](https://www.aihero.dev/ai-coding-dictionary/environment) 访问、一份捕获的工件、或加临时插桩的许可。它不应继续照常提出假说。

## 阶段之间的闸门

阶段是闸门，不是清单。每一扇门在某个具体条件为真之前拒绝打开。

| 闸门 | 必须为真的条件 |
| --- | --- |
| 进入第二阶段 | 一条具名的命令，已实际运行并粘贴了输出，能在这个 bug 上变红 |
| 进入第三阶段 | 复现既已*成功*又已*精简*——剩下的每个元素都是承重的 |
| 进入第四阶段 | 存在 3–5 条排序的、可证伪的假说，每条都陈述自己的预测，在测试任何一条之前先展示给你 |
| 进入第五阶段 | 探针对应到具体预测，一次只动一个变量，每条调试日志带 `[DEBUG-a4f2]` 风格的标签，让清理只需一次 grep |
| 完成 | 原始复现不再重现，插桩已移除，被证实正确的假说写进了提交信息 |

第五阶段有一个值得知道的逃生门。回归测试在修复之前写，但只当存在一个**正确的接缝**时才写——测试要在调用点以真实 bug 模式出现的形式练习它。当唯一可用的接缝太浅时，指示 skill 明说，而不是写一个制造虚假信心的测试。这个缺失本身就是发现，也正是把事后复盘引向 `improve-codebase-architecture` 的东西。

## 常见问题

**它在我只想要直接回答的快速问题上也触发了。**
这是本 skill 被报告最多的问题，而且是真的。尤其在 GPT-5.6-Sol 上，用户报告它对一个问题的普通描述也会触发："模型触发了相当正式的 diagnosing-bugs skill，而不是直接回答。它接着开始构建复现场景——常常构建一个价值有限的模拟场景——然后才给我回应或建议。这导致相当大的回复延迟。"有四个独立的人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上报告了同样的形态。公认的修复是先走更轻的方式，只在问题确实需要时才升级到更重的那个，但那个改动尚未落地。skill 是针对 Claude Code 的调用行为校准的；一个激活阈值更低的 [模型](https://www.aihero.dev/ai-coding-dictionary/model) 会过度触发它。在它升级之前，实际的修复是说出你想要什么（"直接回答这个，别诊断"），或者在你的 [工具链](https://www.aihero.dev/ai-coding-dictionary/harness) 里为它禁用模型调用。

**我能把它指向一个代码库，问性能问题在哪里吗？**
不能。它诊断一个你已经能命名的故障。它的性能分支针对的是有症状的回归——建立基线测量，然后二分，先测量后修复——不是主动扫查。主动版本曾有人 [提议并关闭](https://github.com/mattpocock/skills/issues/431)；目前没有对应 skill。

**它在写修复之前会停下来问我吗？**
不会。只有第三阶段有人类检查点——排序的假说列表在测试任何一条之前展示给你，如果你不在场它就按自己的排序继续。插桩和修复之间没有闸门，所以 Agent 可以在你同意它的根因之前就开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 请求这道闸门，仍然开放。如果你想要，调用时说出来。

**我已经在这份 bug 报告上跑过 `/triage` 了。这是同一份工作的重做吗？**
部分是，而且两个 skill 都不承认。正如一位读者所说："Triage 的第 3 步本质上就是 diagnosing-bugs 第 1–2 阶段的浅层、有界版本，但两个文件都没提对方。"Triage 做的是有界的"这真的是 bug 吗，表面是什么"的过一遍；本 skill 做的是完整版本。先跑 triage 不浪费——它的验证常常给你第一阶段的大部分素材——但预期在这里正经重做一遍，也别指望有交叉引用告诉你这一点。

**它粘贴的复现输出会泄露秘密吗？**
可能。skill 要求 Agent 粘贴调用及其输出，并请求 HAR 文件、日志转储、核心转储之类的工件。这些都没有指令层面上的脱敏。[Issue #674](https://github.com/mattpocock/skills/issues/674) 提出的正是这一点——凭据、token、cookie 和个人数据搭车进入聊天、issue 或 PR——并提议一道脱敏护栏。它开放且未实现。目前把脱敏当成你自己的事，尤其是在输出去任何公开场合之前。

**我的安全扫描器把此 skill 标为高风险。**
Snyk 会标它，而那个标记是误报。它是整套里唯一附带可执行 shell 脚本（`hitl-loop.template.sh`）和运行它的指令以及 curl 开发服务器指令的 skill。附带的 `.sh` 加上运行指令再加上出站 HTTP，足以绊倒静态扫描器。脚本本身只是约 30 行 `read -r -p` 提示，停下来等人类输入。扫描器评的是能力表面，不是已证实的漏洞。

**`/diagnose` 怎么了？**
在 v1.0.0 中改名为 `/diagnosing-bugs`。旧名字不再存在。任何链接着 `/diagnose` 的东西——包装 skill、保存的提示词——都需要更新。

## 有效的标志

- 在提出任何理论之前，它先给你看一条命令和它的红色输出。如果理论先到，skill 就没在运行。
- 它复现的故障正是你报告的故障，不是它路上碰到的近似故障。
- 在开始猜之前它先缩小复现，并能告诉你剩下的每个部分为什么是承重的。
- 在测试任何一条假说之前，你看到 3–5 条排序的假说，每条都带一个你可以证伪的预测。
- 它加的每条调试日志都带 `[DEBUG-a4f2]` 这样的标签，宣布完成时 grep 该标签返回空。
- 提交或 PR 信息点名哪条假说是对的。
- 当它无法用测试锁死 bug 时，它直说，而不是写一个浅的测试。

## 在系统中的位置

`diagnosing-bugs` 是随时可取的独立 skill。有东西坏了时你投入进去，修复和它的回归测试落地后你退出来；它不持有状态，不需要任何前置设置。[ask-matt](https://aihero.dev/skills-ask-matt) 会把"有东西坏了"路由到这里。

两个邻居值得注意。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在真正的发现是"代码没有接缝可以锁死这个 bug"时接下 [交接](https://www.aihero.dev/ai-coding-dictionary/handoff)——推荐在修复落地之后做出，因为那时信息更多。[triage](https://aihero.dev/skills-triage) 在它上游，处理以他人原始报告形式到达的 bug，做的是前两个阶段的较浅版本。
