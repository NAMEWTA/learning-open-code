## 功能说明

`prototype` 写**回答一个问题的可丢弃代码**——这个状态模型感觉对吗，或者这个屏幕应该长什么样。问题在先，决定后面一切东西的形状；一个回答了错误问题的原型是纯粹的浪费，无论它看起来多好。

可丢弃是对代码*怎么写*的约束，不是销毁它的承诺。没有测试、没有超出让它跑起来的错误处理、没有抽象、没有持久化——因为这些东西没有一个能帮你学到你正试图学的那一件事。幸存下来的是答案——折进真实代码——以及原型本身，停在 main 之外的分支上，作为答案出自它的证据。

## 何时使用

输入 `/prototype`，或在任务合适时 [Agent](https://www.aihero.dev/ai-coding-dictionary/agent) 会自动调用它。

在你撞上一个靠谈话无法定案的问题的那一刻使用它——一个你在脑子里装不下其边界情况的状态机、一个你非要看到三个版本并排才能想象的屏幕。[质询](https://www.aihero.dev/ai-coding-dictionary/grilling) 会话恰恰会在这些问题上膨胀：Agent 换着说法，你猜，范围长大去填满不确定性。停止质询，把一次性版本建出来，看一眼，然后一行作答。反过来，如果某个已构建的东西行为异常而你想知道为什么，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)——原型探索要建什么，而不是已建的东西为什么坏了。

你也会不做选择地来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在它的地图上登记 `prototype` 决策 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket)，处理一个 ticket 就是这个 skill。

## 两个分支

问题选择分支，分支产出非常不同的工件：

- **"这个逻辑 / 状态模型感觉对吗？"** —— 一个**可分享的单个 HTML 文件**。一个自包含页面，没有构建、没有服务器，双击就能打开。它带一个带标签的状态面板，每次点击后重新渲染；自由操作按钮，可以按任意顺序戳模型；以及带标签页的**引导走查**——每页一个场景，下方是按压顺序排列的按钮。一切用领域语言标注，所以你可以把它交给设计师、PM 或领域专家，让他们自己感受模型。页面背后的逻辑是一个小的纯模块——一个 reducer、一个状态机、一组函数——保持干净、不碰 DOM，让验证过的版本直接抬进真实代码。
- **"这个应该长什么样？"** —— 同一路由上几个**截然不同**的 UI 变体，从浮动底栏和 `?variant=` URL 参数切换。变体必须在结构上分歧，而不是颜色上；三个微调的卡片网格是墙纸，不是原型。它们尽可能渲染在真实页面里，对着真实数据和真实密度——因为在真空中评判的变体看起来总是没问题。

两者都把状态留在内存里、启动零思考、每一步之后展示完整状态。当你发现自己开始加固其中一个——加测试、接真实数据库、为一个以后可能想要的场景做泛化——你已经不在 prototype 了。

## 原型是一手来源

一个完成的原型留下两样东西，它们去往不同的地方。

**答案**——结论加上它定案的问题——被持久地捕获：一条提交信息、一份 ADR、实现 issue。这是 main 分支保留的东西，折进真实代码。

**原型**是答案所出的可运行证据，它不被删除。它也不属于 main——那里没有要维护它的东西，而且它烂得快——所以它被提交到 main 之外的一次性 `prototype/<name>` 分支，永不合并，实现 issue 上留一个指向该分支的 [上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持干净；探索保持可发现、可重跑，下一个拾起工作的人能接着用。

## 常见问题

**等等——原型不是应该被删除吗？**
不再是了。它以前是：建它、留答案、扔掉代码。对那种做法最尖锐的反对从来不是速度——而是*下一场 [会话](https://www.aihero.dev/ai-coding-dictionary/session) 谁拾起工作，他们有什么可以依据？*原型的一份散文总结会丢掉让它有说服力的东西。所以原型现在被当作 [一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)：它落在 main 之外的 `prototype/<name>` 分支上，实现 issue 指向它。变的是代码住在哪，不是纪律——它仍然从不合并进 main。

**它以前建终端应用。那去哪了？**
逻辑分支现在改为产出一个可分享的单个 HTML 文件。终端应用只能被克隆了仓库、装好运行时的人驱动，而这恰恰排除掉原型最需要其意见的人——设计师、PM、那个知道状态模型本该意味着什么的领域专家。一个双击打开、可以发邮件的自包含文件，任何人都能驱动。底下的纯逻辑模块不变，也仍然是抬进真实代码的那部分。

**一个 Agent 在我本该实现的时候让我 `/prototype`。**
已知问题，而且是个命名问题。`prototype` 是一个泛泛的、讨人喜欢的词，在 tickets 存在后，一个不了解流程的 Agent 会把它读成"显而易见的下一步"，所以即使设计已经在对话里完全定案，它也会被按名推荐。如果你已经知道要建什么，下一步是按 ticket 走 `/implement`。只有当某个具体设计问题真正未决、而且谈话解决不了它时，才伸手够原型。

**我应该在构建任何生产功能之前先原型整个应用吗——比如说，演示给潜在客户看？**
那是穿了本 skill 名字的另一个工件。这里的原型被限定在一个问题上，而"整个应用是什么？"不是一个问题。全应用原型没有自然的停止点，所以它会靠惯性变成生产应用：清理过一遍从不发生，按原型规则写的代码——没有测试、没有错误处理——最终出现在用户面前。如果你需要一个销售演示，刻意把它当演示来建，并明确其中没有一样是生产代码。如果你需要定案一个设计问题，把它削到那个问题上。

**我怎么在它自己的会话里运行它？**
原型住在自己的目录里，会生成一大堆你不想要它留在提问那条线程里的 [上下文](https://www.aihero.dev/ai-coding-dictionary/context)，所以在别处运行它，只把答案带回来。[handoff](https://aihero.dev/skills-handoff) 是双向的桥。

**这难道不是烧 token 最快的办法吗？**
可能是，如果你原型那些靠谈话就能回答的问题，或让一个原型蔓延过整个功能。要紧的比较不是 token 对零；而是 [token](https://www.aihero.dev/ai-coding-dictionary/token) 对建错状态模型、等它有生产调用者之后才发现。保持问题狭窄、运行短暂，花费就保持在相称的水平。

## 有效的标志

- 你能用一句话说出原型存在是为了回答什么问题——而且它写在演示顶部，不只在你脑子里。
- 一个不读代码的人能驱动逻辑演示。他们打开文件、在走查标签页里按按钮、用自己的话描述看到的东西。
- 有人说"等等，那不应该是可能的"或"哈，我以为是 X"。那是*想法*里的 bug，而这正是全部意义。
- UI 变体在布局和信息层级上分歧，而不只是颜色和文案——你得到的反馈是"用 B 的头部配 C 的侧边栏"。
- 它在一坐之间被回答。如果一天后你还在建它，问题太大了；拆开它。
- 结束时，main 包含决策、不含任何原型，实现 issue 指向仍然持有它的分支。

## 在系统中的位置

`prototype` 是**随时可取的独立 skill**——你落进去定案一个设计问题，然后落出来——同时它也是另一个 skill 运行其上的机械装置。

它最大的消费者是 [wayfinder](https://aihero.dev/skills-wayfinder)。一张 wayfinder 地图由**决策 tickets** 构成，而 `prototype` 是一个 ticket 可以是的四种类型之一：当阻塞问题是"这该长什么样"或"这该怎么表现"、任何讨论都解决不了它时用到的那个。Wayfinder 通过制造一件可以对着反应的实在之物来提高一场模糊讨论的保真度，而本 skill 就是那件实在之物被建出来的方式。一个原型 ticket 由答案解决，原型作为资产从地图链接。

其他邻居在它上下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可质询的问题；不可质询的那些来到这里，一行答案回到访谈里。下游，一个验证过的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的定案输入，后者可以内联原型产出的决策密集片段，而不是用散文描述它。其他一切，[ask-matt](https://aihero.dev/skills-ask-matt) 在整套之上为你路由。
