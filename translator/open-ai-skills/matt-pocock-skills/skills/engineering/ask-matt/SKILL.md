# 咨询 Matt

你不需要记住每个技能，直接问就行了。

**流程**是指技能之间的路线。大多数路线沿着一条**主流程**走，两条**入口匝道**汇入其中。其他所有内容要么是独立技能，要么是运行在底层的词汇层。

## 主流程：从想法到交付

大多数工作遵循这条路线。你有一个想法，想要把它构建出来。

1. **`/grill-with-docs`** — 通过访谈打磨想法。只要你在**某个工作目录中工作**，就从这里开始：它是有状态的，会将学到的内容保留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？使用 `/grill-me` — 见独立技能。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是留下书面记录的那个，只要有仓库可以留下记录，它就是两者中更好的选择。）
2. **分支 — 你能在对话中解决所有问题吗？** 如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼看才能确定的 UI），通过原型来绕路，用 **`/handoff`** 双向桥接（原型住在自己的目录里，这正是 `/handoff` 的用武之地 — 见阶段边界）：
   - **`/handoff`** 传出，然后针对该文件开启一个新会话，
   - **`/prototype`** 用一次性代码来回答问题，
   - **`/handoff`** 传回你学到的东西，并在原始想法线程中引用它。
3. **分支 — 这是一个跨会话的构建吗？**
   - **是** → **`/to-spec`**（将线程转为规范），然后 **`/to-tickets`** 将其拆分为 tracer-bullet 工单，每个工单声明其**阻塞边界**。在本地追踪器上，这是 `.scratch/<feature>/issues/` 下每个工单一个文件，按阻塞项优先手工处理；在真正的追踪器上，边界变为原生的阻塞链接，任何阻塞项已完成的工单都可以被领取 — 按工单启动 **`/implement`**，**在每个工单之间 `/clear` 上下文**。每个工单自包含，所以最后一个工单的上下文用完即弃。
   - **否** → 直接在当前上下文窗口中运行 **`/implement`**。

   无论哪种方式，**`/implement`** 在构建每个 issue 时都内部驱动 **`/tdd`** — 每次一个红-绿切片 — 然后在提交前通过运行 **`/code-review`** 来收尾，这是对 diff 的双轴审查（标准 + 规范）。当你只想先测试一个具体行为而不需要完整规范时，单独使用 **`/tdd`**；当你想针对一个固定点审查分支或 PR 时，单独使用 **`/code-review`**。

### 上下文卫生

将步骤 1-3 保持在**一个不间断的上下文窗口**中 — 在 `/to-tickets` 之前不要压缩或清理 — 这样访谈、规范和工单都建立在相同的思考基础上。然后每个 `/implement` 从工单开始，以全新上下文启动。

此处的限制是**[智能区间](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型在此窗口内（当前最先进模型约 150k token）仍能保持敏锐推理。如果会话在 `/to-tickets` 之前接近这个限制，不要硬撑 — 在最近的阶段边界处 `/compact`，然后继续（见阶段边界）。

## 入口匝道

产生工作的起始场景，然后汇入主流程。

- **Bug 和请求堆积如山** → **`/triage`**。它让 issue 通过分类角色流转，生成可供 agent 处理的 issue，后续由 **`/implement`** 领取。

  分类仅适用于**不是你创建的** issue — bug 报告、新功能请求、任何原始到达的内容。`/to-tickets` 生成的工单已经是 agent 可处理的，所以**不要对它们进行分类**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于疑难杂症：一眼看不出的 bug、间歇性抖动、在两个已知良好状态之间悄然而入的回归。它在拥有一个**紧凑反馈回路**之前拒绝推测 — 即一个已经在此 bug 上变红的一条命令 — 然后用回归测试修复。如果真正的发现是没有好的缝合点来锁定 bug，其事后分析会移交给 **`/improve-codebase-architecture`**。

- **一项庞大而模糊的工作 — 一个从零开始的项目或一个大型功能构建，单个会话装不下** → **`/wayfinder`**，这里是认知负担最重的流程。当从起点到终点的路径尚不可见时，它在问题追踪器上绘制一张由**决策工单**组成的**共享地图**，并逐个解决 — 产出的是**决策，而非交付物** — 直到迷雾被驱散、路径清晰可见。如果说 **`/grill-with-docs`** 打磨的是你一个会话内能把握的想法，wayfinder 面向的是你无法在一个会话内把握的想法 — 它更慢、更密集，所以只为这种场景保留它，绝不要用于范围明确的功能。

  当地图清晰后，**它只交接，不构建**：在 **`/to-spec`** 处汇入主流程，`/to-spec` 把地图中相互关联的决策折叠成一份可构建的计划，然后照常走 `/to-tickets` 和 `/implement`。把地图直接绕进 `/implement` 会跳过这次折叠，丢掉关联细节 — 只有当工作量确实很小的时候才直接进入 `/implement`。

## 代码仓健康

不是功能开发 — 是维护。

- **`/improve-codebase-architecture`** — 有空闲时就运行，保持代码仓对 agent 友好。它会暴露**深化机会**；选择一个机会就_生成一个想法_，你可以将其带入主流程的 `/grill-with-docs`。它是找到候选方案的普查；**`/codebase-design`**（见下文）是你设计选中方案的台面。

## 底层词汇

两个由模型调用的参考技能，运行在其他技能的_下层_ — 各自是其词汇的单一事实来源。当**词语**而非流程是问题时，直接使用它们；或者让上面的技能自行拉取。

- **`/domain-modeling`** — 精炼项目的_领域_语言：挑战模糊术语、解决一个超载的词汇（一个 "account" 干了三件事）、将难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动的、保持 `CONTEXT.md` 成为干净词汇表的主动规程。
- **`/codebase-design`** — 深层模块词汇（module、interface、depth、seam、adapter、leverage、locality），用于设计模块的_形状_：在一个干净的缝合点后面、通过一个小接口承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用它。

## 阶段边界

**阶段（phase）** 是会话内的一块工作 — 访谈、实现、QA。在两者之间的**边界**处你有五个选项，而在这整张地图里，选择是其中最模糊的决策：

- **继续（Continue）** — 原地不动。零成本，零损失。
- **`/clear`** — 清空窗口，当这里没有任何东西与下一步相关时。
- **`/handoff`** — 写一个可移植的 markdown 文件。用途狭窄：仅用于**新的 harness**、**新的目录**、**同事**，或在**阶段中途**分叉一个旁路任务。它买到的是可移植性。
- **子 agent（Subagent）** — 把一个范围严格受限的任务送到它自己的窗口，拿回一份报告。
- **`/compact`** — 压缩当前上下文，用它孕育一个新会话。**默认选项**，在树的底部而非第一伸手可及处。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解完整的有序树 — 五个问题、每个分支背后的推理，以及为什么一手资料成本使**继续**成为最先要排除的选项。在**边界处**做决策；在阶段中途，继续推进，或把剩余部分拆成子 agent。

## 独立技能

完全脱离主流程。

- **`/grill-me`** — 与 `/grill-with-docs` 同样无情的访谈，但**无状态**：它不保存任何本地内容，不构建 `CONTEXT.md`。当你**不在某个工作目录中工作**时使用它 — 打磨一个计划、一个设计、一篇文字，任何脚下没有仓库的东西。如果你在某个工作目录中，改用 `/grill-with-docs`：它运行同样的访谈并留下书面记录，所以严格来说它更好。
- **`/grilling`** — 访谈原语本身：轮次、前沿，事实是 agent 的工作、决策是你的。`/grill-me` 和 `/grill-with-docs` 是两条命名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要不带任何包装的访谈时，才直接使用它。
- **`/resolving-merge-conflicts`** — 逐块处理进行中的 merge 或 rebase 冲突，依据**意图**解决 — 追溯到每一侧的原始来源，而不是挑选行 — 然后完成该操作。它从不运行 `--abort`。独立且脱离所有流程：当你已经处于冲突中时使用它。
- **`/prototype`** — 一个回答单个设计问题的小型一次性程序：这个状态模型感觉对吗，或者这个 UI 应该长什么样。"一次性"是对代码写法的约束，而不是销毁它的承诺：答案整合进真实代码，原型本身作为**一手资料**保存在 main 之外的 `prototype/<name>` 分支上，由实现 issue 指向。它是主流程第 2 步中的绕路，但任何时候当设计问题难以在纸面上解决时都可以使用它。
- **`/research`** — 将阅读跑腿工作委托给**后台 agent**：它对照**一手资料**调查问题，然后在仓库中留下一个带引用的 Markdown 文件。你继续工作，让它去阅读。它产生的文件可以带入主流程的 `/grill-with-docs` — 研究喂养思考，而非替代思考。
- **`/to-questionnaire`** — 当挡着你的东西不在你的脑子里、也不在代码库里，而在**别人的脑子里**时，它写一份问卷让对方填写。它是 `/grill-me` 的反面：不是采访你关于主题，而是采访你关于**发送** — 发给谁、你需要回什么 — 并把问题对准差距。回来的内容是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** — 用于只有**人工**能执行的步骤：配置基础设施、设置凭据或 CI secrets、在陌生的第三方后台中点击操作、执行一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，并写入 `.env` 和 GitHub secrets — 这样该流程就不再是你每次都要向 agent 重新解释的东西。模型调用，所以 agent 一碰到只有你能越过的墙就会去取用它。如果 agent 能自己完成，就该自己完成；这是给真正需要人工在回路中的场景用的。
- **`/wait-what`** — 对没说到点的消息的纠正。在对话中途、任何其他技能内部使用它，agent 会带着你缺失的上下文、用 `CONTEXT.md` 的词汇表、以简单的语言重新阐述它刚说过的话。它是事后补救；`/grill-with-docs` 是事前解药，因为及早约定共享语言，才是阻止行话出现的根本办法。
- **`/teach`** — 跨多个会话学习一个概念，将当前目录用作有状态的工作区。
- **`/writing-for-agents`** — 编写 agent 消费的文档的参考：skills、AGENTS.md、被指向的文档。
