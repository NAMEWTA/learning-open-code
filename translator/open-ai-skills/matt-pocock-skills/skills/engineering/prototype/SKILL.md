# 原型

原型是**回答问题的一次性代码**。问题决定形态。

## 选择分支

识别正在回答哪个问题 — 从用户提示、周围代码或用户在线时通过询问来判断：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个单一的、可共享的 HTML 文件 — 包含自由点击按钮和分标签的引导式演练 — 将状态机推向难以在纸面上推理的用例，并且让非开发者也能操作。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在单一路由上生成几个截然不同的 UI 变体，通过 URL 搜索参数和浮动底栏切换。

两个分支产生截然不同的产物 — 选错会浪费整个原型。如果问题确实模棱两可且用户不在线，默认选择更能匹配周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部陈述假设。

## 适用于两者的规则

1. **从一开始就是一次性的，并清楚标记。** 将原型代码放在它实际将被使用的位置附近（靠近它正在原型化的模块或页面旁边），这样上下文是明确的 — 但命名时让随意读者能看出它是原型，而非生产代码。对于一次性 UI 路由，遵循项目已有的任何路由约定；不要发明新的顶层结构。
2. **极易运行。** UI 原型从项目任务运行器中的一条命令启动 — `pnpm <名称>`、`python <路径>`、`bun <路径>` 等。逻辑演示则是一个用户双击即可打开的 HTML 文件。无论哪种方式，启动都不需要思考。
3. **默认不持久化。** 状态驻留在内存中。持久化是原型正在_检验_的东西，而非它应该依赖的东西。如果问题明确涉及数据库，用一个标记着"PROTOTYPE — 请清除我"的临时数据库或本地文件。
4. **跳过润色。** 没有测试，没有超出使原型_可运行_的错误处理，没有抽象。重点是快速学到东西。
5. **呈现状态。** 每次操作后（逻辑）或每次变体切换时（UI），打印或渲染完整的相关状态，让用户看到什么发生了变化。
6. **完成后捕获。** 将任何已验证的决策整合到真实代码中，然后把原型本身作为**一手资料（primary source）** 保留：提交到一条临时分支（不要进 main），并在实现 issue 上留下指向该分支的上下文指针。同时捕获答案——结论以及它所解决的那个问题——记录在 issue 或一次 commit 中。main 分支只保留已验证的决策。
