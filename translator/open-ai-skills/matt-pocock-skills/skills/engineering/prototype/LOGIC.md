# 逻辑原型

一个单一、自包含的 HTML 文件——**可共享的演示**——让任何人通过点击按钮来驱动状态模型。当问题与**业务逻辑、状态转换或数据形态**相关时使用 — 这类问题在纸面上看起来合理，但只有在通过真实案例推动时才会感到不对。

因为它是一个文件、无需安装，你可以把它交给非开发者——设计师、PM、领域专家——让他们亲自感受这个模型。所以它讲他们的语言，而不是代码的语言。

## 何时适合使用这种形式

- "我不确定这个状态机是否处理 X 然后 Y 的边界情况。"
- "这个数据模型是否真的能让我表示……这种情况？"
- "我想在写代码之前感受一下 API 应该是什么样子。"
- 任何有人想要**按下按钮观看状态变化**的场景。

如果问题是"这应该长什么样" — 走错分支了。请使用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

在写代码之前，写下你在为哪个状态模型和什么问题做原型。一段话，放在演示的顶部（一个可见的介绍，而不只是注释）。一个回答了错误问题的逻辑原型纯属浪费 — 明确问题以便稍后检查，无论用户是现在看着还是稍后回来离线查看。

### 2. 将逻辑隔离在可移植模块中

将实际逻辑 — 回答问题的部分 — 放在一个 `<script>` 块中，写成一个小而纯的模块，可以提取出来稍后放入真实代码库。围绕它的页面是一次性的；这个模块不是。

正确的形态取决于问题：

- **纯 reducer** — `(state, action) => state`。适合动作为离散事件且状态是单个值的情况。
- **状态机** — 明确的状态和转换。适合"哪些动作在当前状态下是合法的"本身就是问题的一部分。
- **一组在纯数据类型上的小函数。** 适合没有隐式当前状态的情况 — 只是转换。
- **具有清晰方法面的类或模块**，当逻辑确实拥有持续的内部状态时。

选择最适合所问问题的形态，*而不是*最容易连接到页面的形态。保持纯：无 DOM、无 `document`、无伸手进它的按钮处理器。页面调用它；没有任何东西向相反方向流动。这就是让原型在其生命周期之后仍然有用的关键：一旦问题得到回答，经过验证的 reducer / 状态机 / 函数集就自行提升到真实模块中。

### 3. 构建可共享的 HTML 文件

一个文件，纯 HTML/CSS/JS — 无框架、无打包器、无服务器，一切内联，双击即可打开，并且经得起被邮件转发。任何人都应该能通过打开它来运行它。

为非开发者而写。每个标签都使用**领域语言**，而不是代码 — 按钮和状态读起来像业务，而不是 reducer。用平实的语言解释正在发生什么。

以清晰的层次自上而下布局：

1. **标题和一行说明**，说明这个演示让你探索什么（步骤 1 中的问题）。
2. **当前状态** — 完整的相关状态，渲染为可读的面板（带标签的字段，而不是原始 JSON 转储），每次点击后重新渲染，让变化可见。在有助于非开发者跟上时，指出刚刚发生了什么变化。
3. **自由点击按钮** — 每个动作一个按钮，始终可用，任何人都可以按任意顺序戳弄模型。每次点击分发其动作并重新渲染状态。
4. **引导式演练** — 一组**场景**，每个标签页一个。每个标签页保存一个简短的平实语言场景描述——它设置的处境和要观察什么——以及其下按顺序要**按的按钮**。每个步骤都是一个真实按钮：点击它执行该动作并进入下一步。开始一个演练会重置到已知的初始状态，让场景每次都以相同方式运行。

选择能演示棘手案例的场景——快乐路径、一个棘手的边界案例、一次尝试做本应非法的事情——那些难以在纸面上推理的案例。

保持美观但克制：干净的排版、充足的空间、一种强调色。没有动画、没有花哨效果——没有与状态和按钮争抢注意力的东西。

### 4. 交付

把文件发给他们，或替他们打开。他们会点击演练并在有空时自由点击；有趣的时刻是当他们说"等等，这不应该是可能的"或"嗯，我以为 X 会不一样" — 那些是*想法*中的 bug，这正是整个目的。如果他们想要新的动作或新场景，就添加。原型会演化。

### 5. 捕获答案和原型

一旦原型回答了它的问题，先捕获答案，然后按照 [SKILL](SKILL.md) 描述的方式捕获原型。逻辑特有的映射：经过验证的 reducer / 状态机 / 函数集提升到真实模块中（决策被吸收）；HTML 外壳随临时分支一起保留，让原型作为一手资料存在——而且因为它是一个自包含文件，在那里它仍然可以毫不费力地重新运行。

## 反模式

- **不要添加测试。** 需要测试的原型不再是原型。
- **不要连接到真实数据库。** 使用内存状态，除非问题明确与持久化相关。
- **不要泛化。** 不要"如果我们以后想支持 X 怎么办"。原型回答一个问题。
- **不要将逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可提升。将页面作为纯模块上的一个薄外壳。
- **不要引入框架、打包器或服务器。** 一个接收者双击的文件；一个 React 应用或开发服务器就违背了"可共享"。
- **不要将 HTML 外壳发布到生产环境。** 页面是为手工点击浏览而优化的。其背后的逻辑模块才是值得保留的部分。
