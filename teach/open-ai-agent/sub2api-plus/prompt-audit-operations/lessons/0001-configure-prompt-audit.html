记录用户问了什么

目标：让经过 sub2api-plus 的正常用户提示词也进入“提示词审计 → 事件”，先只记录，不阻断请求。

预计 15 分钟 · 需要管理员账号、可用的 PostgreSQL/Redis、一个 Qwen3Guard 兼容节点

最关键的开关：“保存安全事件”必须开启。只开“启用提示词审计”，默认只保存被标记或判为严重的提示词。

一、先认清两个模型

用户调用的 GPT、Claude、Gemini 等是业务模型。配置页要求填写的是另一个审计模型：sub2api-plus 会把提取出的用户文字发给它判断安全性。这个节点必须兼容 OpenAI Chat Completions，并返回 Qwen3Guard 格式，例如：

Safety: Safe
Categories: None

普通聊天模型即使接口兼容，也可能因不返回这两行而报 invalid_response。项目页面默认模型 ID 是 sileader/qwen3guard:0.6b，但最终要填 Guard 服务实际暴露的 ID。若按 Qwen 官方方式自建 vLLM，则填写 Qwen/Qwen3Guard-Gen-0.6B。

二、按顺序配置

1打开总开关

管理员 → 系统设置 → 功能设置 → 风控中心，开启“启用风控中心”并保存。不开这个总开关，提示词审计页面即使有配置也不会执行。

2添加审计节点

进入“提示词审计 → 配置 → 新增节点”。名称可填 Qwen3Guard，稳定 ID 填 guard-primary；Base URL 填服务根地址，不要填完整的 /v1/chat/completions，系统会自动追加。填写 API Key、实际模型 ID，超时初次可设 10000 ms，单片上限先保留 4000，并启用节点。

Docker 部署时，容器里的 127.0.0.1 是容器自己。Guard 在 Mac 宿主机上时通常使用 http://host.docker.internal:端口；同一 Compose 网络中则使用 Guard 的服务名。
3先点“连接测试”

只有显示连接正常，才继续。若保存 API Key，请为服务设置固定的 TOTP_ENCRYPTION_KEY，否则重启后密钥可能无法解密。

4设置范围与底部开关

审计策略选“全部分组”，九类风险先全选，Worker 保留 4、队列保留 32768。底部开启“启用提示词审计”和“保存安全事件”；关闭“同步阻止”，然后保存。

三、发一条请求并验收

通过真实中转发送一条带唯一标记的请求，例如：AUDIT_TEST_20260828 请只回复 OK。回到“提示词审计”，刷新运行态和事件页。验收标准：

  • 生效模式是 异步只审计，进程、数据库、Redis 和 Guard 节点均健康。
  • “提取成功”和“处理”计数增加，“丢弃”不增加。
  • 事件列表出现该请求；打开详情，在“完整提示词（未脱敏）”看到唯一标记。

异步处理可能延迟几秒。这里保存的是用户编写的提示词，不保存业务模型的正常响应；响应记录不是当前页面可配置的能力。

四、检索练习

判断：某条正常问题没有出现在事件列表，但风险问题能出现。最可能漏了哪个开关？

查看答案

漏了“保存安全事件”。它对应 store_pass_events；关闭时安全请求仍会被审计，但不会入事件表。

还没有 Guard 服务或连接失败时，继续看 自建方法、字段清单与错误排查。内容边界以项目的 覆盖矩阵为准。

完整提示词以未脱敏形式存入 PostgreSQL。上线前应限制管理员权限、告知用户并制定删除周期。
