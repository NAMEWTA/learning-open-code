0002 — 差分渲染引擎深度解析

层级：L3 微观 API 预计时长：14 分钟 学习目标：1 个

学习目标：理解 previousLines 逐行比对算法、三种渲染策略的触发条件与降级路径、CSI 2026 同步输出协议的作用。

1. 渲染调度管线

用户不会直接调用 doRender()。渲染通过 requestRender() 触发，经过节流调度后才执行： 

requestRender()                   // 组件或外部调用
  → process.nextTick()            // 延迟到下一个微任务
    → scheduleRender()            // 16ms 最小间隔节流（约 60fps）
      → doRender()                // 实际渲染入口

16ms 节流是防止高频更新（如流式 LLM 输出）导致渲染风暴。如果两次请求间隔小于 16ms，后一次会被合并到定时器中延迟执行。调用 requestRender(true) 可跳过节流强制立即渲染。

2. 三种渲染策略

doRender() 内部按优先级依次判断，命中即返回：

策略触发条件操作性能
① 首帧渲染 previousLines.length === 0 且尺寸未变 直接输出全部行，不清屏（假定终端干净） O(n)
② 全量重绘 终端宽度变化 / 高度变化（非 Termux）/ 内容收缩 / 变化行超出视口 \x1b[2J\x1b[H\x1b[3J 清屏 + 清滚动缓冲，重新输出全部行 O(n)
③ 增量渲染 以上条件均不满足（最常用） 逐行比对，ANSI 光标移动到变化区，只重写差异行 O(Δ) 变化行数
⚠️ 降级保护：当变化区域的起始行低于上一帧视口顶部（firstChanged < prevViewportTop），或 Kitty 图像行数超出可视范围时，增量渲染会降级为全量重绘，确保画面正确。

3. 逐行比对算法

这是差分渲染的核心——如何找出真正需要更新的行：

// 源码简化（tui.ts doRender 方法）
let firstChanged = -1, lastChanged = -1;
const maxLines = Math.max(newLines.length, previousLines.length);

for (let i = 0; i < maxLines; i++) {
  const oldLine = previousLines[i] ?? "";
  const newLine = newLines[i] ?? "";
  if (oldLine !== newLine) {
    if (firstChanged === -1) firstChanged = i;
    lastChanged = i;
  }
}

// 新增行：追加到末尾的情况
if (newLines.length > previousLines.length) {
  if (firstChanged === -1) firstChanged = previousLines.length;
  lastChanged = newLines.length - 1;
}

算法要点：

  • 纯字符串比对——不解析 ANSI 序列，直接逐行 === 比较，速度极快
  • 新增行识别——当新行数多于旧行数时，即便新增行内容恰好与旧行末尾相同也会被标记为变更（安全优先）
  • 删除行处理——当 firstChanged ≥ newLines.length 时，只清空多余行而不重写任何内容
  • Kitty 图像扩展——图像占多行，比对结果会扩展变化范围以包含完整图像区域

4. ANSI 序列生成与同步输出

确定变化范围后，增量渲染生成以下 ANSI 序列：

// 伪代码——实际序列生成逻辑
buffer = "\x1b[?2026h";              // ① 开始同步输出
buffer += "\x1b[${lineDiff}B";       // ② 光标垂直移动到首变化行
buffer += "\r";                       // ③ 光标回到行首
for (i = firstChanged..lastChanged) { // ④ 逐行覆写
  buffer += "\x1b[2K";               //    清当前行（从光标到行尾）
  buffer += newLines[i];             //    写入新行内容
  if (i < lastChanged) buffer += "\r\n";
}
buffer += "\x1b[?2026l";             // ⑤ 结束同步输出，终端一次性刷新

CSI 2026（Synchronized Output）是关键——终端在收到 \x1b[?2026l 之前缓冲所有输出，收到后才一次性渲染到屏幕。这消除了"先清行再写内容"之间的闪烁间隙。目前主流终端（iTerm2、Kitty、WezTerm、Windows Terminal）均支持此协议。

闭上眼睛，回忆以下内容：

  1. 三种渲染策略分别是什么触发条件？
  2. 逐行比对用的是深度比较还是字符串 ===？为什么？
  3. 如果 firstChanged = 5 但上一帧视口顶部在第 10 行，会发生什么？
点击查看答案

1. 首帧（previousLines 为空）、全量（尺寸变化/收缩/溢出视口）、增量（其他情况）。
2. 字符串 ===，不做 ANSI 解析。因为组件渲染输出已包含完整 ANSI 样式，纯字符串比对足够判断内容是否变化，且速度极快。
3. 触发全量重绘。因为 firstChanged(5) < prevViewportTop(10)，增量渲染无法触及视口上方的行，必须清屏重建。
