0005 — 工具注册与包装管线：自定义工具如何融入 Agent 引擎？

层级：L3 深度实现 预计时长：15 分钟 学习目标：1 个 前置：0002-三层架构
学习目标

理解一条自定义工具从 ToolDefinition → RegisteredTool → AgentTool 的三阶段转换管线，掌握 Wrapper 如何通过 runner.createContext() 将 Agent 上下文注入扩展工具的 execute 方法，以及 动态工具发现（addedToolNames）的巧妙实现。

1. 三阶段转换管线

扩展定义的"原始工具"需要经过三次格式转换，才能被 Agent 引擎调用：

ToolDefinition          RegisteredTool            AgentTool
(扩展定义)        →     (loader 注册)       →     (agent-core 可调用)
┌──────────────┐       ┌──────────────┐         ┌──────────────┐
│ name          │       │ definition   │         │ name          │
│ label         │       │ sourceInfo   │         │ description   │
│ description   │  +    └──────────────┘    +    │ parameters    │
│ parameters    │                               │ execute()     │
│ execute()     │                               │ renderCall()  │
│ renderCall()  │                               │ renderResult()│
│ renderResult()│                               └──────────────┘
└──────────────┘

阶段 1：扩展定义 ToolDefinition

import { defineTool } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

const helloTool = defineTool({
  name: "hello",
  label: "Hello",
  description: "A simple greeting tool",
  parameters: Type.Object({
    name: Type.String({ description: "Name to greet" }),
  }),
  async execute(toolCallId, params, signal, onUpdate, ctx) {
    return {
      content: [{ type: "text", text: `Hello, ${params.name}!` }],
      details: { greeted: params.name },
    };
  },
});

defineTool() 是一个恒等函数——不做任何转换，只保留 TypeScript 泛型推断。它的存在是为了防止 TypeScript 在数组上下文中将 params 类型拓宽为 unknown。

阶段 2：loader 包装为 RegisteredTool

// 在 createExtensionAPI 中
registerTool(tool: ToolDefinition): void {
  extension.tools.set(tool.name, {
    definition: tool,
    sourceInfo: extension.sourceInfo,  // 记录来源：哪个扩展注册的
  });
  runtime.refreshTools();  // 通知 agent-core 工具有变化
}

refreshTools() 是关键——它触发 agent-core 重新读取工具列表，让新注册的工具立即对 LLM 可见。不需要重启或 /reload。

阶段 3：wrapper 包装为 AgentTool

这是最关键的转换。wrapRegisteredTool() 通过 wrapToolDefinition() 创建一个新的 execute 函数，将 ToolDefinition.execute 包装了一层：

export function wrapRegisteredTool(registeredTool: RegisteredTool, runner: ExtensionRunner): AgentTool {
  // wrapToolDefinition 改造 execute：将 runner.createContext() 作为第 5 个参数 ctx
  const tool = wrapToolDefinition(registeredTool.definition, () => runner.createContext());

  const execute = tool.execute;
  return {
    ...tool,
    execute: async (toolCallId, params, signal, onUpdate) => {
      // 记录执行前的活跃工具列表
      const activeBefore = runner.getActiveTools();

      // 调用原始 execute（此时 ctx 已注入）
      const result = await execute(toolCallId, params, signal, onUpdate);

      // 检查执行后是否有新工具被注册（动态工具发现！）
      const activeAfter = runner.getActiveTools();
      const addedToolNames = activeAfter.filter(name => !activeBefore.includes(name));

      return { ...result, addedToolNames };
    },
  };
}
核心设计：ctx 注入。 wrapToolDefinition() 将 Runner 的 createContext() 闭包注入到 AgentTool 的 execute 中，这样扩展的 execute 方法能收到与事件 handler 完全相同的 ctx——有 ui、signal、model 等全部能力。工具执行时的上下文和事件 handler 的上下文是同一个来源。

2. 动态工具发现（addedToolNames）

这是一个精巧的设计——一个工具在执行过程中可能调用 pi.registerTool() 注册新工具。wrapper 通过比较执行前后的活跃工具列表来检测这一点：

// 场景：工具 "init_project" 执行时注册了新工具 "deploy"
pi.registerTool({
  name: "init_project",
  async execute(toolCallId, params, signal, onUpdate, ctx) {
    // 初始化项目...
    
    // 注册新工具——只有项目初始化完成后才有意义
    pi.registerTool({
      name: "deploy",
      description: "Deploy the initialized project",
      // ...
    });
    
    return { content: [{ type: "text", text: "Project initialized" }] };
  },
});

wrapper 检测到 deploy 是新增的工具，将其加入 addedToolNames。Agent 层收到这个信息后，会在下一轮 LLM 调用时把新工具告诉模型。

为什么不在 tool_result 事件中做？ 因为 addToolNames 是 agent-core 的协议字段，不是扩展事件系统的概念。wrapper 是 agent-core 和扩展之间的"翻译层"，它把扩展的副作用（注册了新工具）翻译成 agent-core 能理解的信息（addedToolNames）。

3. 工具的完整能力矩阵

一个 ToolDefinition 不只是 execute——它有 11 个字段，每个都是可选但精心设计的扩展点：

字段类型用途灵活性贡献
namestring（必填）LLM 工具调用标识工具名即 API，无需注册表
labelstring（必填）TUI 中显示的名称人机界面与 LLM 接口分离
descriptionstring（必填）LLM 理解工具的提示词可注入任意的使用指导
parametersTypeBox Schema（必填）LLM 参数约束运行时类型校验
promptSnippetstring（可选）注入系统提示词的摘要控制 LLM 对工具的认知粒度
promptGuidelinesstring[]（可选）LLM 使用指导影响 LLM 的行为策略
renderShell"default" | "self"控制 TUI 渲染壳完全自定义工具的视觉呈现
prepareArguments函数（可选）参数预处理器兼容旧版本 LLM 的参数格式
executionMode"sequential" | "parallel"并发控制工具级别的执行策略
renderCall函数（可选）自定义调用渲染工具调用在 TUI 中的视觉样式
renderResult函数（可选）自定义结果渲染工具输出在 TUI 中的呈现方式

每个可选字段都是一个"钩子点"，让扩展可以精确控制工具在 Agent 对话中的行为（promptGuidelines、executionMode）、外观（renderShell、renderCall、renderResult）和兼容性（prepareArguments）。

4. 总结：为什么扩展能如此灵活？

通过 0002-0005 四节课，我们可以总结出 Pi 扩展系统灵活性的 5 个架构支柱：

  1. 三层分离：loader / runner / wrapper 各司其职，独立演进
  2. 两阶段初始化：stub → bind 确保加载期安全 + 运行时高效共享
  3. 7 种事件分发策略：链式替换、短路取消、阻断修改——每种事件类型用最合适的策略，而不是一刀切
  4. 延迟求值的 ctx：handler 看到的是"当前"状态，而非注册时的"快照"
  5. 三阶段工具管线：ToolDefinition → RegisteredTool → AgentTool，每阶段添加不同维度的元数据（sourceInfo → ctx → addedToolNames），分层解耦

检索练习

  1. 为什么 wrapper 要在 execute 前后对比 getActiveTools()，而不是在 tool_result 事件中检测新工具？
  2. defineTool() 如果不做任何转换，它存在的意义是什么？
  3. ToolDefinition 有 7 个可选字段——如果去掉 renderShell 和 renderCall，扩展还能自定义工具的 TUI 显示吗？
点击查看参考答案
  1. agent-core 使用 addedToolNames 作为协议字段来更新 LLM 的工具列表。tool_result 是扩展事件系统的概念，它的返回值（content/details/isError）被 agent-core 消费的方式不同。wrapper 作为翻译层，把扩展的副作用精确翻译为 agent-core 协议。
  2. 保持 TypeScript 泛型推断。当工具定义放在数组中（如 [toolA, toolB]），TypeScript 会推断为联合类型并丢失 params 的类型信息。defineTool 是一个 identity function 技巧，强制 TypeScript 保留原始类型参数。
  3. 不能。去掉 renderShell 和 renderCall 后，工具仍能正常执行——execute 不受影响。但 TUI 中的显示会使用默认样式（标准的"执行中"和"完成"壳）。renderShell/ renderCall/ renderResult 纯粹是视觉层的自定义，不影响工具的逻辑。
