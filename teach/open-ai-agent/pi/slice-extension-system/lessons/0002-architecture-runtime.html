0002 — 三层架构与共享运行时：为什么这样设计？

层级：L3 深度实现 预计时长：14 分钟 学习目标：1 个 前置：0001-流程总览
学习目标

理解 Pi 扩展系统 Loader / Runner / Wrapper 三层分离 的设计动机，掌握 ExtensionRuntime 共享状态 + 两阶段初始化 模式为何能同时实现「加载期安全隔离」和「运行时高效共享」。

1. 三层架构的"为什么"

很多插件系统会把"发现、加载、调度、包装"全部塞进一个类里。Pi 没有这样做。它拆成了三个文件，各司其职：

层文件核心职责对外暴露什么
Loaderloader.ts发现、编译、实例化扩展LoadExtensionsResult
Runnerrunner.ts事件分发、上下文创建、生命周期ExtensionRunner 实例
Wrapperwrapper.ts将扩展工具适配为 Agent 可调用的格式wrapRegisteredTool()
核心洞察：三层分离的本质是「关注点分离 + 生命周期错位」。 Loader 只在启动时运行一次，Runner 在整个会话生命周期中持续运行，Wrapper 在工具注册和调用时运行。把它们拆开，每一层都可以独立演进、独立测试、独立替换。

1.1 如果不用三层架构会怎样？

❌ 单块式（假设的反模式）

把所有逻辑塞进一个 ExtensionManager 类：jiti 加载、模块缓存、事件调度、工具包装、上下文创建全在一起。修改加载逻辑可能牵连事件分发代码，工具注册的 bug 可能影响整个扩展系统的启动。

✅ Pi 的三层分离

loader.ts 只管"把 .ts 文件变成 Extension 对象"，runner.ts 只管"在合适的时间调用合适的 handler"，wrapper.ts 只管"把自定义工具格式转成 Agent 格式"。彼此通过清晰的数据结构（Extension、RegisteredTool）通信。

2. 共享运行时的两阶段初始化

这是扩展系统最精妙的设计之一。理解它需要先看两个需求：

  • 加载阶段安全：扩展的 factory 函数执行时，Agent 会话还没创建、模型注册表还是空的。此时调用 pi.sendMessage() 应该立即报错，而不是静默失败或产生未定义行为。
  • 运行时高效：所有扩展共享同一个运行时实例，避免每个扩展维护独立的状态副本。扩展 A 注册的 flag 值，扩展 B 能读取到。

如何同时满足这两个需求？答案是 stub → bind 模式：

// 阶段 1：loader 创建 runtime，action 方法全是 throwing stub
export function createExtensionRuntime(): ExtensionRuntime {
  const notInitialized = () => {
    throw new Error("Extension runtime not initialized...");
  };
  return {
    sendMessage: notInitialized,   // ← 此时调用会抛错
    setModel: notInitialized,      // ← 同理
    flagValues: new Map(),         // ← 但纯数据字段立即可用
    // ...
  };
}

// 阶段 2：runner.bindCore() 替换 stub 为真实实现
bindCore(actions, ctxActions) {
  this.runtime.sendMessage = actions.sendMessage;   // ← 替换！
  this.runtime.setModel = actions.setModel;         // ← 替换！
  // ...
}
设计精妙之处： flagValues（配置数据的 Map）从始至终可用——它不需要依赖 Agent 会话。但 sendMessage 这类需要 Agent 的方法，在 bind 之前是 throwing stub。这种字段级别的生命周期分化，比「整个 runtime 不可用」的方式精确得多。

此外，registerProvider() 采用了一种中间策略——队列模式：在 bind 之前调用会先排队（存入 pendingProviderRegistrations），bind 之后批量刷新。这样既允许扩展在 factory 中声明 provider，又不会在模型注册表未就绪时执行注册。

// 扩展 factory 中调用（加载时）
pi.registerProvider("my-provider", config);
// → 此时 runtime.registerProvider 是队列版本，存入 pendingProviderRegistrations

// bindCore() 之后
for (const { name, config } of this.runtime.pendingProviderRegistrations) {
  modelRegistry.registerProvider(name, config);  // 批量刷新
}
this.runtime.registerProvider = (name, config) => {
  modelRegistry.registerProvider(name, config);  // 替换为直接注册
};

3. ExtensionContext 的延迟求值

事件 handler 收到的 ctx（ExtensionContext）不是一个"快照对象"，而是通过 createContext() 每次动态创建的。它的每个属性都是 getter，在访问时才从 Runner 获取最新值：

createContext(): ExtensionContext {
  return {
    get ui() { return runner.uiContext; },        // 运行时可变
    get cwd() { return runner.cwd; },             // 运行时可变
    get model() { return getModel(); },           // 每次重新查询
    isIdle: () => runner.isIdleFn(),              // 每次都重新调用
    get signal() { return runner.getSignalFn(); }, // 每次重新获取
    // ...
  };
}

为什么不用快照？因为事件 handler 可能跨多次 Agent 循环执行。一个 handler 在注册时捕获的 model 可能已过时，当 handler 真正被调用时（几轮对话之后），agent 可能已经切换了模型。延迟求值保证了 ctx 始终反映当前状态。

4. stale 引用检测：assertActive + invalidate

当一个扩展调用 ctx.newSession() 或 ctx.reload() 后，旧的 ExtensionRunner 会被替换。但旧的 pi 和 ctx 引用可能还在闭包中：

// 危险！这个 ctx 在 newSession 后就 stale 了
pi.on("session_start", async (_event, ctx) => {
  await ctx.newSession({ withSession: async (newCtx) => {
    // ✅ newCtx 是新的、有效的
    // ❌ 外层的 ctx 已经 stale，调用会抛错
    ctx.ui.notify("这行会抛错！");
  }});
});

实现上，Runner 调用 invalidate() 设置 staleMessage，所有 ctx 属性访问和 pi API 调用都会先调用 assertActive()：

private assertActive(): void {
  if (this.staleMessage) {
    throw new Error(this.staleMessage);
  }
}

错误信息还会指导用户如何修复："Move post-replacement work into withSession"。

检索练习

  1. 为什么 flagValues（Map 类型）不需要 stub，而 sendMessage 需要？
  2. registerProvider() 的队列模式解决了什么问题？
  3. ExtensionContext 使用 getter 而非快照——这解决了什么场景下的问题？
点击查看参考答案
  1. flagValues 是纯内存数据结构（Map），不依赖 Agent 会话或模型注册表，任何时候都是安全的。sendMessage 需要将消息注入 Agent 的对话流，这依赖会话对象已存在。
  2. 允许扩展在 factory 函数中声明 provider（加载期），而不要求模型注册表已就绪。队列在 bindCore 后批量刷新，之后替换为直接注册——实现了"声明期安全 + 运行时即时生效"。
  3. 事件 handler 可能在注册之后很久（多次对话循环后）才被调用。延迟求值确保 ctx.model、ctx.signal 等始终反映 Agent 的当前状态，而非注册时的"冻结快照"。
