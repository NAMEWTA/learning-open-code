0003 — 事件系统的拦截链设计：如何实现灵活又不失控？

层级：L3 深度实现 预计时长：14 分钟 学习目标：1 个 前置：0002-三层架构
学习目标

理解扩展系统 7 种事件分发策略 的差异——为什么不是所有事件都用同一个 emit()，以及 链式替换、短路取消、错误隔离 三种模式如何组合出既灵活又安全的拦截体系。

1. 通用 emit()：遍历 + try-catch + 短路

这是最基础的事件分发模式，处理 session_start、turn_start、agent_end 等不涉及数据修改的事件。

async emit<TEvent extends RunnerEmitEvent>(event: TEvent) {
  const ctx = this.createContext();
  for (const ext of this.extensions) {
    const handlers = ext.handlers.get(event.type) ?? [];
    for (const handler of handlers) {
      try {
        const result = await handler(event, ctx);
        // session_before_* 事件特有：handler 返回 cancel = true 则短路
        if (this.isSessionBeforeEvent(event) && result?.cancel) {
          return result;
        }
      } catch (err) {
        this.emitError({ extensionPath: ext.path, event: event.type, error: ... });
        // ← 关键：不抛出，不影响后续 handler
      }
    }
  }
}

这里有三个关键设计决策：

  • 所有扩展共享同一个 ctx：ctx 是延迟求值的，所以所有 handler 看到的都是当前的 Agent 状态
  • try-catch 包裹每个 handler，不包裹整个循环：一个 handler 抛异常，不影响同扩展的其他 handler，也不影响其他扩展
  • session_before_* 的 cancel 短路：一旦有扩展说 "cancel"，立即停止遍历——后面的扩展不再收到事件
设计精妙之处： cancel 短路不是 "抛异常"，而是 "正常 return"。这很重要——cancel 是预期行为，不应该污染错误日志。异常路径和预期路径分离，让错误追踪变得干净。

2. 链式替换：emitContext / emitBeforeProviderRequest / emitMessageEnd

这三类事件的核心区别在于：handler 不仅"观察"事件，还"修改"事件数据，且 后一个 handler 接收前一个 handler 修改后的结果。

// 以 emitContext 为例——每个 handler 都可能修改 messages 数组
async emitContext(messages: AgentMessage[], signal?: AbortSignal) {
  let current = messages;
  for (const ext of this.extensions) {
    for (const handler of ext.handlers.get("context") ?? []) {
      if (signal?.aborted) break;
      const result = await handler({ type: "context", messages: current }, ctx);
      if (result?.messages) {
        current = result.messages;  // ← 链式替换！
      }
    }
  }
  return current; // ← 返回最终版本
}

这种模式让多个扩展可以"管道式"地处理数据：

  • 扩展 A 注入一段系统指令到 messages
  • 扩展 B 看到的是 A 修改后的 messages，再追加自己的上下文
  • 扩展 C 裁剪掉敏感信息

顺序很重要！ 扩展按加载顺序（也是 extensions 数组的顺序）执行。项目本地的扩展先加载，全局扩展后加载，所以全局扩展能"看到"本地扩展的修改结果。

事件链式替换的数据特殊约束
contextmessages 数组支持 AbortSignal 中断
before_provider_requestpayload（发给 LLM 的 HTTP body）任意替换，无类型约束
message_endmessage 对象替换后必须保持原 role 不变
before_agent_startsystemPrompt 字符串还收集 messages 数组

3. 阻断修改：tool_call / tool_result / user_bash

这三类事件 handler 可以决定 是否阻止 或 如何修改 工具的执行。

tool_call — 阻止执行或修改参数

pi.on("tool_call", async (event, ctx) => {
  if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
    return { block: true, reason: "危险操作已拦截" };
  }
  // 也可以修改参数（mutable!）
  if (event.toolName === "write" && event.input.filePath?.includes(".env")) {
    event.input.filePath = event.input.filePath + ".backup";
  }
});

关键设计： event.input 是可变的——handler 可以直接修改它。后续 handler 看到的是前一个 handler 修改后的 input。没有重新校验——这是有意为之，允许扩展绕过原始 schema 校验实现自己的逻辑。

tool_result — 修改工具输出

pi.on("tool_result", async (event, ctx) => {
  // 拦截敏感信息
  if (event.toolName === "bash") {
    event.content = event.content.map(c => ({
      ...c,
      text: c.text?.replace(/API_KEY=\w+/g, "API_KEY=***")
    }));
    return { content: event.content };  // 返回修改后的内容
  }
});

user_bash — 替换 bash 执行器

pi.on("user_bash", async (event, ctx) => {
  // 扩展可以完全接管 bash 执行
  return {
    operations: myCustomBashOperations,  // 自定义执行器
    // 或者直接返回结果，跳过执行
    // result: { stdout: "cached result", stderr: "", exitCode: 0 }
  };
});

4. 错误隔离的三层防护

Pi 的错误处理不是"一个 try-catch 包住所有"，而是分三层：

层级范围行为
单个 handlertry-catch 包裹每个 handler捕获后 emitError 通知监听器，继续下一个 handler
单个扩展for 循环遍历扩展的 handlers一个扩展的 handler 失败，不影响其他扩展
整个事件事件分发完成后Agent 主流程不中断——扩展错误永远不会导致 Agent 崩溃
// emitError 的实现——通知所有注册的错误监听器
emitError(error: ExtensionError): void {
  for (const listener of this.errorListeners) {
    listener(error);  // 通常是 console.warn，在 TUI 中可能是通知
  }
}
为什么不在 handler 失败时阻断事件？ 因为无法判断失败是"故意的"还是"意外的"。如果扩展 A 的 bug 导致它抛异常，不应该阻止扩展 B 正常工作。这叫 fail-open 策略——宁可让一个异常 handler 被跳过，也不能让整个拦截链失效。

检索练习

  1. context 事件的链式替换和 session_before_switch 的 cancel 短路，有什么区别？
  2. 为什么 tool_call 事件中修改 event.input 后不做重新校验？
  3. 如果扩展 A 的 tool_call handler 抛异常，扩展 B 的同一个事件 handler 还会执行吗？
点击查看参考答案
  1. 链式替换是"数据管道"——每个 handler 修改数据并传递给下一个。cancel 短路是"否决权"——一个 handler 说 cancel，整个操作中止，后续 handler 不执行。前者用于数据转换，后者用于权限控制。
  2. 这是有意设计——允许扩展在参数校验之后、执行之前对参数做二次处理。例如：扩展可以把相对路径转绝对路径，或者把简写命令展开为完整命令。重新校验会阻止这类合法操作。
  3. 会。try-catch 只包裹单个 handler，不包裹整个遍历循环。扩展 A 的异常被捕获并 emitError 后，循环继续执行扩展 B 的 handler。
