0004 — 扩展模块动态加载机制：TypeScript 如何在运行时变原生代码？

层级：L3 深度实现 预计时长：14 分钟 学习目标：1 个 前置：0002-三层架构
学习目标

理解 Pi 如何使用 jiti (Just-In-Time TypeScript Import) 实现扩展的动态加载，掌握 virtualModules（Bun binary）vs aliases（Node.js） 两套模块解析策略，以及 扩展缓存机制 如何避免重复编译。

1. 为什么用 jiti 而不是 ts-node 或 Node.js loader？

扩展是 TypeScript 文件，但 Pi 在运行时才加载它们。不能用 tsc 预编译（用户可能随时添加新扩展），也不能用 ts-node（太重，启动慢）。jiti 是 unjs 生态的轻量级方案：

import { createJiti } from "jiti/static";

const jiti = createJiti(import.meta.url, {
  moduleCache: false,           // 不使用模块缓存？注意后面会解释
  virtualModules: VIRTUAL_MODULES,  // Bun binary 模式
  alias: getAliases(),             // Node.js 开发模式
  tryNative: false,                // Bun binary 模式下强制 jiti 处理所有 import
});

const module = await jiti.import(extensionPath, { default: true });
const factory = module as ExtensionFactory;

jiti 的核心能力是即时编译——读到 .ts 文件，当场转译成可执行的 JS，整个过程对调用方透明。扩展开发者只需要写 TypeScript，不需要配置编译步骤。

关键洞察： jiti 的 import 返回的是一个模块的 exports，而不是文件内容。这意味着扩展的 import { Type } from "typebox" 会被 jiti 解析——但 jiti 需要知道 typebox 在文件系统中的位置。这就是 virtualModules 和 alias 要解决的问题。

2. 双模式模块解析：virtualModules vs aliases

Pi 有两种运行形态，模块解析策略完全不同：

运行模式场景解析策略为什么？
Bun binary 用户下载编译好的 pi 可执行文件 virtualModules 编译后的二进制里没有 node_modules 和文件系统上的包路径，所有 pi 包（agent-core、tui、ai、coding-agent）都被 Bun 打包进了二进制。virtualModules 告诉 jiti："这些 import 符号指向内存中的这些对象"。
Node.js 开发 开发者在 monorepo 中运行 tsx src/cli.ts aliases monorepo 中有完整的文件系统，包之间的引用可以解析到 packages/*/dist/ 的实际路径。aliases 告诉 jiti："@earendil-works/pi-coding-agent 指向 ../../coding-agent/dist/index.js"。

virtualModules 的完整映射：

const VIRTUAL_MODULES: Record<string, unknown> = {
  // TypeBox —— 扩展定义工具参数 schema 的核心库
  "typebox": _bundledTypebox,
  "typebox/value": _bundledTypeboxValue,
  "@sinclair/typebox": _bundledTypebox,

  // Pi 内部包 —— 扩展可 import 的 API 类型
  "@earendil-works/pi-agent-core": _bundledPiAgentCore,
  "@earendil-works/pi-tui": _bundledPiTui,
  "@earendil-works/pi-ai/compat": _bundledPiAiCompat,
  "@earendil-works/pi-coding-agent": _bundledPiCodingAgent,

  // 旧命名空间的兼容映射 (mariozechner → earendil-works)
  "@mariozechner/pi-coding-agent": _bundledPiCodingAgent,
  // ... 其他旧命名空间
};

这些虚拟模块在文件顶部被 静态 import：

import * as _bundledTypebox from "typebox";
import * as _bundledPiCodingAgent from "../../index.ts";

注意注释："These MUST be static so Bun bundles them into the compiled binary." 只有在顶层静态 import，Bun 才会在编译二进制时把它们打包进去。如果动态 require，它们会被遗漏。

3. 扩展缓存：避免重复编译

每次 /reload 都重新用 jiti 编译所有扩展会很慢。Pi 使用了一个基于 CWD + generation counter 的缓存机制：

let extensionCacheCwd: string | undefined;
let extensionCacheGeneration = 0;
const extensionCache = new Map<string, ExtensionFactory>();

function useExtensionCacheCwd(cwd: string): ExtensionCacheToken {
  const resolvedCwd = resolvePath(cwd);
  // 如果 CWD 变了，清除所有缓存
  if (extensionCacheCwd !== undefined && extensionCacheCwd !== resolvedCwd) {
    clearExtensionCache();
  }
  extensionCacheCwd = resolvedCwd;
  return { cwd: resolvedCwd, generation: extensionCacheGeneration };
}

缓存的有效性检查——三重验证：

function isCurrentCacheToken(cacheToken?: ExtensionCacheToken): boolean {
  return cacheToken !== undefined
    && extensionCacheCwd === cacheToken.cwd           // CWD 没变
    && extensionCacheGeneration === cacheToken.generation; // 没被 clear 过
}

Generation counter 的作用： 当用户在同一 CWD 下显式调用 clearExtensionCache() 时，generation 递增，旧的 cache token 全部失效。这是一种比"清空 Map"更优雅的失效策略——不需要追踪哪些地方持有旧引用。

4. 三层发现规则：从哪儿找到扩展？

export async function discoverAndLoadExtensions(
  configuredPaths: string[],  // settings.json 中配置的路径
  cwd: string,
  agentDir: string,           // ~/.pi/agent/
): Promise<LoadExtensionsResult> {
  // 1. 项目本地：cwd/.pi/extensions/
  const localExtDir = path.join(cwd, ".pi", "extensions");
  addPaths(discoverExtensionsInDir(localExtDir));

  // 2. 全局：~/.pi/agent/extensions/
  const globalExtDir = path.join(agentDir, "extensions");
  addPaths(discoverExtensionsInDir(globalExtDir));

  // 3. 显式配置的路径（settings.json 或 -e 参数）
  for (const p of configuredPaths) {
    // 如果是目录 → 扫描目录或读 package.json 的 pi.extensions
    // 如果是文件 → 直接添加
    addPaths([p]);
  }
}

任一目录下的发现规则：

  1. 直接 .ts/.js 文件 → 当作扩展入口
  2. 子目录有 index.ts/index.js → 加载 index
  3. 子目录有 package.json 且含 pi.extensions → 加载该字段声明的入口

关键限制：不递归。 只扫描一层。如果子目录没有 index 也没有 package.json，它会被忽略。这避免了扫描 node_modules 等大目录的性能问题。

设计精妙之处： 三层顺序决定了优先级。项目本地扩展先加载 → 先注册的事件 handler 先执行 → 本地扩展可以（通过 cancel）否决全局扩展的行为。这种顺序设计本身就是一种权限模型。

检索练习

  1. 为什么 Bun binary 模式下需要 tryNative: false？
  2. 缓存机制为什么要同时检查 CWD 和 generation？只检查 CWD 够不够？
  3. 如果扩展的 package.json 没有 pi.extensions 字段但根目录有 index.ts，扩展会被加载吗？
点击查看参考答案
  1. Bun binary 中没有原生 Node.js 模块解析（没有文件系统路径）。如果 jiti 尝试用原生方式解析 import，会失败。tryNative: false 强制所有 import 都走 jiti 的 virtualModules，确保所有依赖都从内存中的打包对象获取。
  2. 不够。CWD 不变但用户可能修改了扩展代码后执行 /reload。此时需要 clearExtensionCache() → generation 递增 → 旧缓存失效 → 重新 jiti 编译。Generation counter 提供了一种"不追踪引用"的失效机制。
  3. 会。发现规则中 index.ts/index.js 的优先级低于 pi.extensions——先检查 package.json manifest，没有才回退到 index 文件。这是故意设计的：简单扩展不需要 package.json，复杂扩展用 manifest 声明入口。
